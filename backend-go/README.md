# Go Backend

Owner: Madi

The Go service owns BiletFlow's business API: events and ticket types, paid-sales activation,
checkout with simulated payment, tickets (signed QR + A4 PDF), orders and refunds, door check-in,
promo campaigns, support cases, analytics and history, notifications, and platform moderation.
Identity (accounts, roles, JWTs) stays in the Python service. See `docs/architecture.md` and the
shared contract `docs/openapi.yaml`.

## Structure

```text
backend-go/
├── cmd/api/main.go            configuration, background jobs, HTTP server
└── internal/
    ├── app/                   assembles every feature behind the auth middleware
    ├── auth/                  Python RS256 JWT verification + live identity, staff lookup
    ├── platform/              PostgreSQL, embedded migrations, JSON/errors, audit log,
    │   └── migrations/        settings, identity directory cache, rate limiting
    ├── event/                 events, ticket types, Event Admin assignments (handler → service → repository)
    ├── commerce/              activation, checkout, payment simulator, QR + PDF tickets, orders, refunds
    ├── promo/                 campaigns, server-side discounts, atomic redemption, Campaign QR links
    ├── checkin/               scanner API for the mobile check-in app
    ├── support/               support cases and message threads
    ├── analytics/             organizer dashboard, event analytics, activity timeline
    ├── notify/                in-app notifications, kk/ru/en templates, e-mail outbox
    ├── admin/                 moderation, payments monitoring, settings, reports, CSV export
    └── testutil/              runs the real app against PostgreSQL in tests
```

Layering inside each feature stays handler → service → repository. Business rules that depend on
concurrency are enforced in PostgreSQL: the event row is locked `FOR UPDATE` while reserving, a
check-in is a conditional `UPDATE … WHERE status='valid'`, and promo redemption is a conditional
increment, so they hold across any number of Go instances.

## Data

Go applies its own migrations at startup (`internal/platform/migrations`, tracked in
`go_schema_migrations`). Python keeps the `identity_*` tables; Go stores user UUIDs without foreign
keys into them and caches display data in `user_directory`, refreshed from `/api/users/me` on every
authenticated request. The audit log is append-only (enforced by a trigger).

## Configuration

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | PostgreSQL, e.g. `postgres://biletflow:…@localhost:5432/biletflow?sslmode=disable` |
| `JWT_PUBLIC_KEY_FILE`, `JWT_ISSUER`, `JWT_AUDIENCE`, `JWT_KEY_ID`, `IDENTITY_URL` | see `docs/python-go-auth.md` |
| `TICKET_QR_SECRET` | ≥ 32 characters; signs admission QR codes (generated by `scripts/init_local.py`) |
| `APP_URL` | public web address used in e-mails and Campaign QR links |
| `SMTP_ADDR`, `MAIL_FROM` | mail relay (Mailpit `mailpit:1025` in Compose) |
| `TRUST_PROXY=1` | honour `X-Forwarded-For` for rate limiting behind a reverse proxy |

## Run locally

```bash
python3 scripts/init_local.py          # from the repository root, once
docker compose up --build -d --wait python go
curl http://localhost:8080/ready
```

## Test

Tests run the whole application against a disposable PostgreSQL database; each test gets its own
schema. Without `GO_TEST_DATABASE_URL` the database tests are skipped.

```bash
createdb biletflow_go_test
export GO_TEST_DATABASE_URL='postgres://biletflow:PASSWORD@localhost:5432/biletflow_go_test?sslmode=disable'
gofmt -l . && go vet ./... && go test -race ./...
```

The suite includes concurrency tests (20 buyers for 5 tickets, a promo code limited to 3 used by 10
buyers at once, 8 devices scanning one ticket) and keeps the original Week 1–4 event and auth tests.

Payments, refunds, payouts and identity checks are a clearly labelled **simulation** (SRS §3.2):
no money moves and no card number or IIN is stored.
